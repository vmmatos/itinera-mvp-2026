# Proposal: localizing trip-planning content (agent output + PDF)

Status: **proposal only, not implemented**. This PR ships the site-wide UI language
infrastructure (`users.language`, `/settings`, `@nuxtjs/i18n`). It does not change
what language the multi-agent pipeline writes in, nor the PDF export. Those are
separate, larger changes described here for later scoping.

## Why this is a separate effort

The UI-string i18n work (this PR, and PR2's full-site key extraction) is a
frontend-only concern: static labels translated via `en.json`/`pt.json`. Trip
content is different — it's free text *generated by LLM calls* across several
services (`preference-agent`, `orchestrator-agent`, `finance-agent`), and it also
needs to reach the PDF export service (`services/sharing`). Getting this wrong
risks breaking the strict JSON response contracts these agents rely on.

## Where the language needs to flow

1. **Source of truth**: `users.language` (this PR). A trip is owned by a user
   (`trips.owner`), so `WorkflowEngine.buildInitialContext(trip)`
   (`services/orchestrator/src/services/WorkflowEngine.ts:99`) is the natural
   place to load the owner's language onto `WorkflowContext`, once, per run.
2. **Threading through the pipeline**: every `agentCaller.call*` site
   (`services/orchestrator/src/services/AgentCaller.ts`, lines 78-220 —
   `callFinanceAgent`, `callPreferenceAgentSlots`, `callOrchestratorMerge`,
   `callLogisticsPlan`, etc.) would need an explicit `language` argument added
   to its request body. `AgentCaller.post()` (lines 57-72) has no locale concept
   today — this is new surface, not a rename.
3. **Per-agent prompts**: each concrete agent (`PreferenceAgent`,
   `ItineraryMerger`, `ConflictAnalyzer`, `CompromiseGenerator`,
   `ProposalRefiner`, `AlternativeFinder`) loads a static `.txt` prompt file at
   construction time (e.g. `services/orchestrator-agent/src/config/prompts/merge.txt`).
   Recommended approach: **append a language directive at call time**, not
   duplicate the prompt file per language. Something like appending
   `"Respond in {languageName}. Keep all JSON field names and structure in
   English — only translate free-text field values."` to the system prompt
   string right before the `complete()` call, driven by the `language` value
   threaded in from step 2.

## The risk that makes this non-trivial

These prompts define strict JSON response schemas (see `merge.txt`, `propose.txt`)
that downstream code parses directly. A language instruction must target only
the free-text fields (`title`, `description`, negotiation summaries) — never
field names, enum values, or structure. This needs deliberate prompt wording
and test coverage (a scenario test asserting the JSON still parses when
`language=pt`) before it can ship, not just a blanket "respond in Portuguese."

## PDF export (`services/sharing`)

`services/sharing/src/templates/itinerary.ts` hardcodes English chrome
(`"Travel"`, `"Meals"`, `"Weather Forecast"`, footer text). Since this service
isn't a Nuxt app, it can't use `@nuxtjs/i18n`, but it can import the same
`en.json`/`pt.json` dictionaries built for the frontend (they're plain JSON —
no framework dependency) and pick the trip owner's `language` at generation
time (`services/sharing/src/routes/export.ts:76-106`). The LLM-generated
itinerary fields inherit whichever language the agents were instructed to
answer in (see above) — the PDF template itself doesn't need to translate
that part, only its own static labels.

## Known compounding risk

`AgentCaller` has no fetch timeout (tracked separately, unfixed on `main`).
Language-instructed calls may run slightly slower or need more retries if a
model struggles with the added instruction — this makes the missing-timeout
issue more likely to surface in practice once this work starts. Worth fixing
before or alongside this effort, not after.

## Suggested sequencing (not scoped/estimated here)

1. Add `language` to `WorkflowContext` + thread through `AgentCaller`.
2. Append the language directive to prompts one agent at a time, with a
   scenario test per agent asserting JSON-parseability in a non-English run.
3. Wire the same dictionaries into `services/sharing`'s PDF template.
4. Only after 1–3 are stable, consider whether the agent-to-agent conversation
   stream shown in the negotiate UI (`useAgentStream.ts`) needs any additional
   handling — it currently just relays whatever text the agents produced, so
   it should localize for free once step 2 lands, with no separate UI change.
